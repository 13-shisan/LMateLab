This report covers the local-only structure catalog and VASP input builder.
Nothing was pushed, deployed, submitted to Slurm, or fetched from an external
materials service.

## 1. Source Decision

The MVP uses a small catalog bundled with the application and constructs the
structures through the already-pinned `ASE 3.23.0` dependency. It does not call
Materials Project, COD, NOMAD, AFLOW, OQMD, or another runtime API.

Reasons:

- six requested structures do not justify an external service dependency;
- offline construction is deterministic and works on an isolated compute node;
- there is no API key, rate limit, remote availability, or changing upstream
  payload in the user workflow;
- source version, seed parameters, generated files, and SHA-256 values can be
  recorded in one local manifest.

The representative lattice values are starting geometries, not convergence or
scientific-acceptance evidence.

## 2. Catalog

The fixed first catalog contains:

- `MoS2_monolayer`
- `WS2_monolayer`
- `MoSe2_monolayer`
- `WSe2_monolayer`
- `graphene`
- `hBN`

Only `MoS2_monolayer` is marked compatible with the existing executable
`mos2_v1` workflow. The other five structures are build, preview, and download
only and cannot expand the current calculation allowlist.

## 3. Controlled Transformations

Operator-controlled inputs are bounded on both the API schema and builder:

- in-plane repeats: `1..6` along a and b;
- layer count: `1..8` using explicit AA stacking;
- vacuum on each slab side: `8..40 Angstrom`;
- layer separation: `3..10 Angstrom`;
- in-plane strain: `-5..5 percent`;
- final structure size: at most `200` atoms.

Unknown IDs, path-like IDs, non-finite values, values outside the ranges, and
structures above the atom limit fail closed.

## 4. VASP Input Bundle

The generated ZIP contains exactly these flat files:

- `POSCAR`
- `INCAR`
- `KPOINTS`
- `POTCAR.spec`
- `manifest.json`
- `README.txt`

`POTCAR` is never read or included. `POTCAR.spec` records only the required
element order. The manifest records the source metadata, transformation
parameters, workflow-compatibility flag, and hashes for the generated inputs.
The INCAR and KPOINTS are controlled review drafts, not claims of convergence.

## 5. Authorization And Network Boundary

- Viewer can list the catalog but cannot build or download an input bundle.
- Operator can build a preview and download the generated bundle.
- The browser calls only fixed application routes.
- The builder performs no HTTP request, shell command, Slurm action, filesystem
  traversal, or Agent built-in tool call.

## 7. Remaining Gates

- Additional structures need a reviewed catalog entry and provenance update.
- Alternative stacking registries, twist angles, defects, surfaces, adsorbates,
  and arbitrary bulk transformations are outside this MVP.
- The generated package does not submit a job or decide scientific success.
- Real Linux/Slurm validation remains a separate migration gate.

## 8. KPOINTS Review And Queue Handoff

Implemented on `2026-08-22`:

- KPOINTS may be entered manually or generated by the deterministic mock Qoder
  adviser. The mock result is explicitly advisory and makes no convergence
  claim.
- In-plane mesh values are server-bounded to `1..60`; the third value is fixed
  to `1` for the supported 2D workflow.
- Reviewed relax, SCF, and DOS meshes are included in the canonical draft JSON,
  input hash, and materialized files. BAND retains the immutable
  `Gamma-M-K-Gamma` line path from `mos2_v1`.
- The web review dialog exposes the generated POSCAR, the three editable mesh
  definitions, the controlled INCAR parameters, template, and fixed four-step
  task before submission.
- Confirmation uses the existing application sequence: structure upload, draft
  save, server validation, and workflow start. Qoder never calls `sbatch`,
  `scancel`, or the coordinator.
- Only `MoS2_monolayer + mos2_v1 + relax -> SCF -> BAND -> DOS` enables the
  queue handoff. Other catalog structures remain preview/download-only.
